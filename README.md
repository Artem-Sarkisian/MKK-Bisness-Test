# Асинхронный процессинг платежей

Сервис принимает платёж, обрабатывает его через эмулятор шлюза и отправляет
результат на webhook. API отвечает после сохранения платежа, не дожидаясь
обработки. Один consumer выполняет весь сценарий.

## Стек

Python 3.14, FastAPI, Pydantic v2, SQLAlchemy 2.0 async, PostgreSQL,
RabbitMQ / FastStream, Alembic, Docker Compose. Зависимости и хеши пакетов
зафиксированы в `uv.lock`. Основа образов: Python 3.14.10 и PostgreSQL 18.6 на Alpine 3.24,
RabbitMQ 4.4.0. При сборке применяются доступные обновления системных пакетов. Используются стабильные выпуски, без beta/RC.

## Запуск

Нужны Docker и Docker Compose v2. Устанавливать Python или uv на хост не нужно.

```sh
cp .env.example .env
```

Замените `API_KEY`, `POSTGRES_PASSWORD`, `RABBITMQ_PASSWORD` в `.env`.
Для паролей удобно использовать шестнадцатеричные строки, например вывод
`openssl rand -hex 24`: такие значения не требуют URL-кодирования.
API-ключ должен содержать от 16 до 128 символов. `.env` исключён из Git.
`DATABASE_URL` и `RABBITMQ_URL` нужны для локального запуска; внутри Compose
адреса формируются автоматически из паролей.

```sh
docker compose up -d --build
docker compose ps
docker compose logs -f consumer
```

Миграции автоматически применяются перед запуском API. Consumer запускается
после готовности API и RabbitMQ. Базовый Compose содержит четыре сервиса:
`postgres`, `rabbitmq`, `api`, `consumer`.

- API: `http://localhost:8000`.
- RabbitMQ Management: `http://localhost:15672`, пользователь `payments`,
  пароль из `RABBITMQ_PASSWORD`.
- БД и AMQP-порт в базовой конфигурации не опубликованы на хост.
- Данные PostgreSQL и RabbitMQ сохраняются в именованных Docker volumes.

Остановка с сохранением данных: `docker compose down`.
`docker compose down -v` **удаляет данные** этого Compose-проекта.

## API

Все API-эндпоинты требуют `X-API-Key`. Ключ проверяется до чтения тела
запроса; повторяющиеся заголовки ключа отклоняются. Автоматические `/docs`, `/redoc` и
`/openapi.json` отключены. Отсутствующий или неверный ключ возвращает `401`.

В следующих примерах задайте `API_KEY` в окружении терминала значением из `.env`.

### Создание платежа

```sh
curl -i http://localhost:8000/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{
    "amount": "123.45",
    "currency": "RUB",
    "description": "Заказ 42",
    "metadata": {"order_id": 42},
    "webhook_url": "https://your-public-domain.example/payments"
  }'
```

Домен в примере — заглушка: замените его адресом вашего получателя либо
используйте локальную демонстрацию ниже.

Ответ `202 Accepted`:

```json
{
  "payment_id": "b0fea71d-66ed-438f-8aac-a2f68df45e34",
  "status": "pending",
  "created_at": "2026-11-10T08:00:00Z"
}
```

Все пять полей тела обязательны. `description` может быть пустым, максимум
1000 символов; `metadata` — JSON-объект до 16 KiB в сериализованном виде.
Валюта: `RUB`, `USD` или `EUR`. Сумма положительная, до 16 цифр перед точкой
и двух после неё (`NUMERIC(18, 2)`); в ответах передаётся строкой.
Лишние поля запрещены. Некорректные данные возвращают `422`.
NUL, некорректные Unicode-последовательности и нечисловые значения
`NaN`/`Infinity` не принимаются; вложенность metadata ограничена 32 уровнями.
Тело запроса ограничено 64 KiB, включая потоковую передачу без
Content-Length; превышение возвращает `413`. Чтение тела ограничено
10 секундами (`408`); сжатые тела не поддерживаются (`415`). Ошибки валидации
не содержат исходные значения полей. При временной недоступности БД API
возвращает `503` с `Retry-After: 1`; запрос можно повторить с тем же ключом.

`Idempotency-Key`: от 1 до 128 символов, латинские буквы, цифры, `.`, `_`,
`:`, `-`. Повтор с тем же ключом и теми же нормализованными данными
возвращает `202`, идентификатор, исходное время создания и текущий статус
существующего платежа. Новый платёж и событие не создаются. Изменённые данные
с уже использованным ключом возвращают `409`. Порядок ключей JSON и записи
суммы `10.0` / `10.00` не влияют на сравнение.

### Получение платежа

```sh
curl http://localhost:8000/api/v1/payments/PAYMENT_ID \
  -H "X-API-Key: $API_KEY"
```

Ответ `200`: `payment_id`, `amount`, `currency`, `description`, `metadata`,
`status`, `idempotency_key`, `webhook_url`, `created_at`, `processed_at`.
Неизвестный UUID — `404`, некорректный UUID — `422`.
Времена содержат часовой пояс UTC; `processed_at` равен `null` до результата.

## Обработка и гарантии

1. API в одной транзакции сохраняет строки в `payments` и `outbox`.
   Уникальное ограничение в PostgreSQL защищает от конкурентных запросов
   с одинаковым ключом.
2. Фоновая задача в процессе consumer читает готовые записи Outbox через
   `FOR UPDATE SKIP LOCKED`. Сообщения публикуются с `persistent`,
   `mandatory` и publisher confirms. Запись отмечается опубликованной
   только после подтверждения маршрутизированной публикации.
3. Один обработчик читает `payments.new` с `prefetch=1` и ручным ACK.
   Эмулятор ждёт 2–5 секунд асинхронно: вероятность успеха 90%, отказа 10%.
   После сохранения результата обработчик отправляет webhook.
4. При ошибке обработчик атомарно сохраняет следующую попытку в Outbox
   и только затем подтверждает исходное сообщение. При исчерпании попыток
   аналогично сохраняется событие для DLQ.

Топология RabbitMQ:

| Exchange (direct, durable) | Routing key | Queue (durable) |
| --- | --- | --- |
| `payments` | `payments.new` | `payments.new` |
| `payments.dead` | `payments.dlq` | `payments.dlq` |

Повторы планируются через `outbox.available_at`, отдельный retry-consumer
не нужен. DLQ публикуется явно через Outbox и подтверждение брокера,
чтобы исходное сообщение не терялось при недоступности маршрута DLQ.

Доставка — **at least once**: сбой между публикацией и отметкой Outbox
может привести к дубликату. Обработчик проверяет сохранённый прогресс и номер
попытки. Транзакционная advisory-блокировка сериализует обработку одного
платежа. Завершённый платёж не проводится заново; подтверждённо доставленный
webhook повторно не отправляется. Старые сообщения после перехода к следующей
попытке безопасно подтверждаются.

## Webhook и retry

Отправляется `POST` с JSON:

```json
{
  "event_id": "d83180f6-4df2-4bc7-bce1-3b0e76e95915",
  "event_type": "payment.completed",
  "payment_id": "b0fea71d-66ed-438f-8aac-a2f68df45e34",
  "status": "succeeded",
  "amount": "123.45",
  "currency": "RUB",
  "processed_at": "2026-11-10T08:00:03+00:00"
}
```

- Любой `2xx` означает доставку. Остальные коды, включая перенаправления,
  сетевые ошибки и таймаут, считаются ошибкой доставки.
- Таймаут — 5 секунд. Три попытки всего: первая и два повтора с задержками
  2 и 4 секунды после ошибки. Публикация может произойти позже из-за
  нагрузки, перезапуска или недоступности инфраструктуры.
- Результат платежа сохраняется до webhook. Ошибка уведомления не меняет
  `succeeded` / `failed`. Во всех повторах тело и `event_id` одинаковые.
- Получатель обязан распознавать повторы по `event_id`: он мог принять запрос,
  а ответ мог потеряться. Гарантии «ровно один раз» для HTTP нет.
- Счётчик попыток сохраняется до внешних действий. Прерванная аварией попытка
  считается использованной; после восстановления планируется следующая.
  Это ограничивает число обращений, даже если процесс падает во время HTTP.
- По завершении третьей неуспешной попытки событие попадает в `payments.dlq`.
  Автоматического возврата из DLQ нет. `reason` содержит краткий код ошибки.
- Повторы публикации Outbox не ограничены тремя попытками: событие остаётся
  в БД до успешной публикации. Сбой инфраструктуры до начала сохраняемой
  попытки не расходует её бюджет.
- Повреждённые сообщения, неизвестные платежи и невозможные номера попыток
  отправляются в DLQ без бессмысленной обработки. Для некорректного сообщения
  сохраняется хеш тела, а не потенциально чувствительные данные.

Разрешены HTTP/HTTPS URL без встроенных учётных данных. Перенаправления
отключены. Внутренние, loopback и служебные IP запрещены, включая результаты
DNS-разрешения; соединение использует проверенные адреса. `WEBHOOK_ALLOWED_HOSTS`
позволяет точечно разрешить доверенный локальный приёмник для разработки.
API-ключ не отправляется получателю. HMAC-подпись не реализована, поскольку
обмен секретами для webhook не задан в требованиях.

## Локальная демонстрация webhook

Дополнительный Compose-файл поднимает тестовый получатель и разрешает только
его имя `webhook` для внутренних запросов:

```sh
docker compose -f compose.yaml -f compose.demo.yaml up -d --build
```

Создайте платёж с одним из адресов:

| URL | Поведение |
| --- | --- |
| `http://webhook:8080/success` | `204` сразу |
| `http://webhook:8080/flaky` | Два ответа `503`, затем `204` |
| `http://webhook:8080/fail` | Всегда `503`, затем DLQ |
| `http://webhook:8080/slow` | Ответ через 10 секунд, превышает таймаут |

Полученные запросы: `curl http://localhost:18081/events`.
Получатель предназначен только для локальной демонстрации, хранит события
в памяти и не входит в базовые четыре сервиса.

## Проверки

### Полный набор в Docker

Используются отдельная БД `payments_test` и RabbitMQ vhost `payments_test`.
Тесты очищают только эту БД. Для первоначальной подготовки:

```sh
docker compose -f compose.yaml -f compose.test.yaml up -d --wait postgres rabbitmq
docker compose exec postgres createdb -U payments payments_test
docker compose exec rabbitmq rabbitmqctl add_vhost payments_test
docker compose exec rabbitmq rabbitmqctl set_permissions -p payments_test payments '.*' '.*' '.*'
docker compose -f compose.yaml -f compose.test.yaml run --rm --build tests
```

Сервис `tests` находится в отдельном профиле и не запускается при обычном
`up`: `run tests` включает его явно. Создание БД и vhost выполняется один раз; при следующих прогонах достаточно
последней команды. Миграции тестовой БД применяются автоматически.

Проверяются API и авторизация, конкурентная идемпотентность, откат транзакции,
Outbox, потеря маршрута RabbitMQ, настоящий consumer и DLQ, обработка
повреждённого JSON, повторная доставка, восстановление после прерывания,
экспоненциальная задержка, HTTP-ошибки и защита адресов webhook.

### Локальная разработка

```sh
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

Без `TEST_DATABASE_URL` / `TEST_RABBITMQ_URL` интеграционные проверки
пропускаются; это **не полный прогон**. Для их запуска задайте адреса
тестовой БД и vhost. `compose.test.yaml` публикует PostgreSQL на `55432`
и AMQP на `55672`, только на loopback. Не используйте рабочую БД для тестов.

### Проверка запущенного стека со сбоями

```sh
docker compose -f compose.yaml -f compose.test.yaml -f compose.demo.yaml up -d --build
uv run python tests/verify_http.py
uv run python tests/verify_stack.py
```

В `.env` должны быть актуальные локальные `DATABASE_URL` и `RABBITMQ_URL`
с портами `55432` и `55672`. Первый скрипт проверяет HTTP-границы, авторизацию, некорректный ввод,
потоковую передачу и медленные запросы, сверяя отсутствие записей в БД.
Второй скрипт выполняет реальные запросы к API и webhook,
проверяет задержки, DLQ, останавливает и восстанавливает RabbitMQ и PostgreSQL, аварийно
завершает consumer во время доставки и запускает его снова. Оба предназначены
только для этого локального Compose-проекта; не запускайте его против чужой
или рабочей инфраструктуры.

## Принятые трактовки и границы

- 10% ошибок эмулятора — окончательный отказ платежа (`failed`), а не
  техническая ошибка, требующая повторной оплаты. Уведомление отправляется
  и для успешного, и для отклонённого платежа.
- «Три попытки» означает три попытки обработки сообщения всего. Успешно
  завершённые этапы пропускаются при повторе. При чисто техническом сбое
  до получения результата платёж может остаться `pending`, а задача уйти
  в DLQ: сервис не выдумывает результат операции.
- Один обработчик управляет всеми этапами. Классы шлюза, HTTP-клиента,
  публикации и доступа к данным разделяют обязанности; дополнительных
  consumers для оплаты или уведомлений нет.
- Эмулятор не выполняет реального списания. При подключении настоящего
  шлюза потребуется его идемпотентный ключ и сверка результата для окна
  между вызовом шлюза и сохранением результата в БД.
- Гарантии рассчитаны на сохранность БД, volumes и восстановление
  инфраструктуры. Один узел RabbitMQ не обеспечивает отказоустойчивость
  к потере диска. Репликация и резервное копирование вне объёма задания.
- История Outbox сохраняется; автоматическая очистка и интерфейс ручного
  разбора DLQ не реализованы.


## Разделение проверок

`test_gateway.py` детерминированно подменяет случайность и ожидание эмулятора;
`test_processing.py` подменяет шлюз и отправитель HTTP для точной проверки
состояний. Эти тесты не доказывают работоспособность сетевой доставки.
`test_api.py` использует настоящий PostgreSQL, но вызывает API внутри процесса.
`test_broker.py` запускает настоящий FastStream consumer с RabbitMQ и БД.
`test_webhooks.py` отправляет запросы настоящему локальному HTTP-серверу.
`verify_http.py` и `verify_stack.py` работают с запущенными контейнерами через
TCP/HTTP, PostgreSQL и RabbitMQ; сетевые компоненты там не подменяются.
Сам платёжный шлюз остаётся эмулятором согласно ТЗ.

Рабочий образ не содержит uv/pip или инструментов тестирования. API и consumer
работают непривилегированным пользователем, с read-only filesystem,
отключёнными Linux capabilities и запретом повышения привилегий. Отдельный
слой сборки/тестирования использует uv и зафиксированные зависимости.
PostgreSQL запускается сразу от пользователя postgres; неиспользуемый
root-only вспомогательный бинарный файл исключён из образа.
Для публичного production-развёртывания дополнительно нужны TLS-терминация,
лимиты частоты/конкурентности запросов, мониторинг, резервные копии и
регулярное обновление образов. Они не заменяются результатом тестового задания.
